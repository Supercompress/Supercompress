How to shrink a large git diff before an LLM code review

By Arjun Shah

A large pull request can be too big for one prompt, and even when it fits, most of the diff is lockfile churn, context lines and files unrelated to your question. Trim it with git first, then keep only the diff lines that answer what you are reviewing for.

Why does a big diff overflow the context window?

A pull request often mixes lockfiles and generated files with the real code change. Each hunk also carries context lines around the edit, and whitespace-only churn can fill more of the prompt than the lines you care about. Unrelated files in the same branch add still more. Plain truncation cuts the end of the diff regardless of the question; see how compression compares with truncation. A model asked to review a truncated diff will not know what it did not see.

What should I trim with git first?

Start with a cheap overview, then shrink the unified diff before you call any API. Pathspec exclusion leaves matching files out. -U1 (or --unified=1) keeps 1 line of context instead of the default of 3. --ignore-all-space (-w) ignores whitespace when comparing lines; it also hides whitespace-only changes that matter in Python, YAML and Makefiles, so use it only when whitespace is not meaningful. git diff --stat and --name-only give an overview. The A...B range compares from the merge base.

git diff --stat origin/main...HEAD
git diff -U1 origin/main...HEAD -- . ':(exclude)*lock*' ':(exclude)dist/'

These steps are free and deterministic, so do them before any compression.

Why label every diff line with its file?

SuperCompress keeps whole lines. A + or - line on its own does not say which file it came from, and the @@ hunk header may be dropped. Drop the diff --git, index, --- and +++ lines and prefix every remaining line with path | , so any kept line still names its file:

src/calc.py | @@ -10,3 +10,4 @@
src/calc.py |  def add(a, b):
src/calc.py | -    return a + b
src/calc.py | +    return a + b + carry
src/calc.py | +

A kept line can lose its surrounding hunk, so a reviewer (human or model) should open the full diff for anything important. The compressed diff is for finding what to look at, not a replacement for reading changed files.

How do I compress the diff with the SuperCompress API?

curl -X POST https://www.supercompress.dev/api/v1/compress \
  -H "X-API-Key: $SUPERCOMPRESS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"context": "<labelled diff lines>", "query": "Which changes could break existing callers?"}'
import os
import subprocess

import requests

API_URL = "https://www.supercompress.dev/api/v1/compress"
BASE = "origin/main"  # compare against this branch
QUESTION = "Which changes could break existing callers, and which new code paths have no test?"
MAX_CHARS = 120000
EXCLUDE = [":(exclude)*lock*", ":(exclude)*.min.js", ":(exclude)dist/", ":(exclude)vendor/"]


def git(*args):
    return subprocess.run(["git", *args], check=True, capture_output=True, text=True, encoding="utf-8").stdout


def labelled_lines(base):
    """One line per diff line, each starting with the file path."""
    rng = f"{base}...HEAD"
    files = git("diff", "--name-only", rng, "--", ".", *EXCLUDE).split("\n")
    for path in filter(None, files):
        diff = git("diff", "-U1", "--ignore-all-space", rng, "--", path)
        for line in diff.split("\n"):
            if line.startswith(("diff --git", "index ", "--- ", "+++ ")):
                continue  # the label carries the path, so drop the file header
            if line:
                yield f"{path} | {line}"


def js_len(s):
    return len(s.encode("utf-16-le")) // 2  # the API counts UTF-16 units


def segments(lines, max_chars):
    buf, size = [], 0
    for line in lines:
        text = line + "\n"
        if buf and size + js_len(text) > max_chars:
            yield "".join(buf)
            buf, size = [], 0
        buf.append(text)
        size += js_len(text)
    if buf:
        yield "".join(buf)


kept_parts = []
for segment in segments(labelled_lines(BASE), MAX_CHARS):
    kept = segment  # fail open: default to the original segment
    try:
        r = requests.post(
            API_URL,
            headers={"X-API-Key": os.environ["SUPERCOMPRESS_API_KEY"]},
            json={"context": segment, "query": QUESTION},
            timeout=60,
        )
        r.raise_for_status()
        kept = r.json().get("compressed_text") or segment
    except requests.RequestException:
        pass
    kept_parts.append(kept if kept.endswith("\n") else kept + "\n")

print("".join(kept_parts))

The context field is limited to 120,000 characters per call, counted as JavaScript string length (UTF-16 units). Longer input returns HTTP 422 with "context too long (120k max)". Empty context returns 422 with "context required". Send one segment per call. The example fails open: if the request errors, it keeps the original segment. SuperCompress is extractive and query-aware: it selects whole lines from the original rather than writing a summary, so the lines it keeps stay as written; preprocessing may rewrite JSON before lines are chosen. It works per line, which is why every diff line must carry its own file path. Lines that do not match the question are dropped. Each response reports original_tokens and kept_tokens, which are estimates, not provider-billed totals. When the saving would be too small the call passes through: passthrough is true and compressed_text is the original.

What question should I send?

Specific review questions work: "Which changes could break existing callers?", "Where is user input handled without validation?", "Which new code paths have no test?". A generic query like "summarize this text" returns a broader digest and query_mode: "dump". Run one compression per question rather than one for "everything".

When should I skip compression?

Skip it for small diffs that already fit the window. When you need a line by line review of every change, review file by file instead. For security-sensitive changes where a missed line matters, compressed output tells you where to look, so read the full diff for those.

How do I know it helped?

Log original_tokens and kept_tokens (estimates) per segment, compare the review comments with and without compression on a few real pull requests, and check each comment against the full diff.

Frequently asked questions

Will the model see the whole diff?

No. It sees only the kept lines. Open the full diff for anything important; the compressed result is for finding what to look at, not a replacement for reading changed files.

Does it work on binary files or renames?

The API only sees text. git diff prints a one-line notice for binary files, which is kept or dropped like any other line. Renames show up as path changes in the labelled lines when you include those paths.

Should I still exclude lockfiles?

Yes. Pathspec exclusions with git remove lockfiles and generated trees for free and deterministically, so do that before any compression.

Do I need a question?

Yes, for a targeted result. Without a query, or with a generic one like "summarize this text", the API returns a broader digest and labels the response query_mode "dump".
